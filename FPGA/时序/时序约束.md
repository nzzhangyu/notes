# FPGA 时序约束：从 STA 模型到 Vivado/XDC 工程流程

> 一句话总结：时序约束不是“让报告变绿”，而是把设计的真实时钟关系、外部接口预算和功能例外准确告诉 STA；只有约束完整且正确，正 slack 才有意义。

## 背景与范围

本文面向具备数字电路基础、正在使用 AMD Vivado/XDC 的工程人员。内容先讲厂商无关的静态时序分析（Static Timing Analysis, STA），再说明 Vivado 的约束命令与检查流程。

本文不提供具体器件、板卡或外部芯片的真实时序参数。代码中的数值均为**演示值**，使用前必须根据原理图、PCB 走线、外部器件数据手册、FPGA 型号与工程时钟方案重新计算。

## 结论摘要

- 先定义时钟，再定义时钟关系和 I/O 环境，最后才添加具有功能依据的时序例外。
- setup 看最大数据延迟，hold 看最小数据延迟；降低时钟频率通常不能修复 hold 违例。
- `set_input_delay`、`set_output_delay` 描述 FPGA 边界外部的时序关系，不是 FPGA 内部延迟。
- `set_false_path`、`set_clock_groups`、`set_multicycle_path` 不能仅为了消除负 slack 而使用。
- CDC/RDC 安全性由结构、协议和验证保证；切断 STA 分析不等于跨域安全。
- 最终签核必须基于完整布线后的时序报告，并确认没有遗漏时钟、I/O delay 或未约束端点。

## 一、总：建立完整的 STA 认知

### 1. 时序约束究竟在约束什么

STA 不通过输入激励逐周期仿真，而是枚举合法时序路径，在指定的时钟和工作条件下检查数据能否按时到达、是否过早变化。

常见的四类数据路径：

| 路径类型 | 起点 | 终点 | 主要约束来源 |
| --- | --- | --- | --- |
| 寄存器到寄存器 | 寄存器时钟端触发的数据 | 寄存器数据端 | 时钟定义与时钟关系 |
| 输入到寄存器 | FPGA 输入端口 | 寄存器数据端 | `set_input_delay` + 内部时钟 |
| 寄存器到输出 | 寄存器输出 | FPGA 输出端口 | 内部时钟 + `set_output_delay` |
| 输入到输出 | FPGA 输入端口 | FPGA 输出端口 | 通常使用虚拟时钟与 I/O delay，或明确的 max/min delay |

组合逻辑只是路径的一部分；“片内/片外”不能替代对 startpoint、endpoint、launch clock 和 capture clock 的识别。

### 2. Launch、Capture、Arrival、Required 与 Slack

- **Launch edge**：源寄存器发起数据的有效时钟沿。
- **Capture edge**：目的寄存器按设计意图捕获该数据的有效时钟沿。
- **Data Arrival Time**：数据实际到达终点的时间。
- **Data Required Time**：数据必须到达或最早允许到达的边界。
- **Slack**：实际时序与要求之间的余量。

Vivado 的基本关系为：

$$
Setup/Recovery\ Slack = Required\ Time - Arrival\ Time
$$

$$
Hold/Removal\ Slack = Arrival\ Time - Required\ Time
$$

Slack 大于等于 0 表示该项检查通过；Slack 小于 0 表示违例。常见汇总指标：

- `WNS`：Worst Negative Slack，最差 setup slack。
- `TNS`：Total Negative Slack，setup 负 slack 总和。
- `WHS`：Worst Hold Slack，最差 hold slack。
- `THS`：Total Hold Slack，hold 负 slack 总和。

`WNS < 0` 只能证明存在 setup 违例，不能单独证明根因是逻辑级数、布线、扇出、skew 还是约束错误。

### 3. Setup 与 Hold 的统一模型

定义时钟偏斜：

$$
T_{skew}=T_{capture\_clock}-T_{launch\_clock}
$$

同一时钟域下，可用下面的近似式帮助理解。实际 Vivado 报告会展开源/目的时钟路径、抖动与不确定度。

#### 3.1 建立时间检查

$$
T_{period}+T_{skew}
\ge T_{cq,max}+T_{data,max}+T_{setup}+T_{uncertainty,setup}
$$

setup 检查使用最大数据延迟，关注数据是否“到得太晚”。

#### 3.2 保持时间检查

$$
T_{cq,min}+T_{data,min}
\ge T_{hold}+T_{skew}+T_{uncertainty,hold}
$$

hold 检查使用最小数据延迟，关注新数据是否“到得太早”。由于它检查相近时钟沿，单纯增大时钟周期通常无效。

> 注意：不同资料对 `Tskew` 的正方向定义可能相反。使用公式前必须先写明定义，工程判断以 Vivado timing path 中的 Source Clock Delay、Destination Clock Delay、Clock Path Skew 和 Clock Uncertainty 为准。

### 4. 不只 Setup/Hold

| 检查 | 典型对象 | 含义 |
| --- | --- | --- |
| Setup | 同步数据路径 | 数据在捕获沿之前稳定足够久 |
| Hold | 同步数据路径 | 数据在捕获沿之后保持足够久 |
| Recovery | 异步控制释放 | 类似异步控制端的 setup 检查 |
| Removal | 异步控制释放 | 类似异步控制端的 hold 检查 |
| Pulse Width | 时钟/控制脉冲 | 高、低电平宽度满足器件要求 |

FPGA 寄存器的 setup/hold requirement 会随器件系列、speed grade、PVT、原语与分析角变化，甚至可能出现负值。不能用“Xilinx FPGA 普遍为某个固定数值”代替实际报告。

## 二、分：逐类建立约束

### 5. 约束目标与设计假设

写 XDC 前先形成约束清单：

| 项目 | 必须确认的内容 |
| --- | --- |
| 主时钟 | 来源端口、频率、占空比、抖动 |
| 衍生时钟 | 源时钟、生成点、分频/倍频/相位 |
| 时钟关系 | 同步、异步、物理互斥、逻辑互斥 |
| 输入接口 | 外部 launch clock、`Tco_min/max`、数据/时钟 PCB 延迟 |
| 输出接口 | 外部 capture clock、`Tsetup/Thold`、数据/时钟 PCB 延迟 |
| CDC/RDC | 跨域结构、复位释放策略、验证方式 |
| 时序例外 | 功能依据、对象范围、被取消或改变的检查 |

### 6. 主时钟：`create_clock`

**适用范围：AMD Vivado/XDC。** 正确命令是 `create_clock`，不是 `creat_clock`。

```tcl
# 示例：端口输入的 100 MHz、50% 占空比主时钟
create_clock -name sys_clk \
    -period 10.000 \
    -waveform {0.000 5.000} \
    [get_ports sys_clk]
```

原则：

- 尽量在时钟进入设计的边界点创建主时钟。
- `-period` 单位通常由工程时间单位决定，Vivado 常见为 ns。
- 不要因名称相似而推断两个时钟同步。
- 同一对象确需多个时钟时，应理解 `-add` 的含义，并检查是否引入多时钟分析。

### 7. 虚拟时钟

虚拟时钟没有连接到物理端口，常用于描述外部器件的参考时钟或纯组合 I/O 路径。

```tcl
# 示例值：外部系统参考时钟 100 MHz
create_clock -name io_virtual_clk -period 10.000
```

虚拟时钟的价值是把“外部接口规范”与“FPGA 内部时钟树”分开。它不会自动建立与内部时钟的关系；必要时必须保证周期、波形及相关假设与真实系统一致。

### 8. Generated Clock：`create_generated_clock`

当时钟由分频器、PLL/MMCM 输出或逻辑生成，并与源时钟保持确定关系时，应保留这种派生关系。

```tcl
# 示例：源时钟经过寄存器/逻辑二分频后，在目标引脚建立衍生时钟
create_generated_clock -name clk_div2 \
    -source [get_pins u_div/clk_in] \
    -divide_by 2 \
    [get_pins u_div/clk_out]
```

注意：

- 精确的 `-source` 与目标对象取决于网表结构。
- AMD 时钟 IP 通常可产生自动派生时钟；应先用 `report_clocks` 检查，再决定是否手工补充。
- 不要把本应相关的 generated clock 另建为无关主时钟，否则可能丢失正确相位关系。

### 9. 时钟关系

| 关系 | 含义 | 常见处理 |
| --- | --- | --- |
| 同步 | 有共同源且相位/周期关系可确定 | 保持正常 STA |
| 异步 | 无固定相位关系 | 先验证 CDC，再选择合适例外 |
| 物理互斥 | 两个时钟不会同时物理存在 | `set_clock_groups -physically_exclusive`，需事实依据 |
| 逻辑互斥 | 时钟同时存在，但逻辑选择保证不会同时作用于相关路径 | `set_clock_groups -logically_exclusive`，需证明选择关系 |

异步组示例：

```tcl
# 示例：clk_a 与 clk_b 确认无固定相位关系，且 CDC 结构已审查
set_clock_groups -asynchronous \
    -group [get_clocks clk_a] \
    -group [get_clocks clk_b]
```

**分析后果：**两组时钟之间的常规时序分析被切断，但这不会验证同步器、握手、FIFO 或数据一致性。使用前后都应运行 `report_clock_interaction` 与 `report_cdc`。

### 10. 输入时序约束

`set_input_delay` 表示外部数据相对于指定参考时钟到达 FPGA 输入边界的时间范围。

系统同步输入的概念模型：

$$
InputDelay_{max}=T_{co,max}+T_{dataPCB,max}-T_{clockPCB,min}+Margin
$$

$$
InputDelay_{min}=T_{co,min}+T_{dataPCB,min}-T_{clockPCB,max}-Margin
$$

这里把数据和时钟走线分别写出，可避免含义不明的 `Tskew` 符号。真实计算还可能包含外部时钟树、抖动和数据手册定义的测试条件。

```tcl
# 以下 3.2 ns / 0.6 ns 仅为示例，不是推荐值
set_input_delay -clock io_virtual_clk -max 3.2 \
    [get_ports {data_in[*]}]
set_input_delay -clock io_virtual_clk -min 0.6 \
    [get_ports {data_in[*]}]
```

DDR 接口通常还要按上升沿/下降沿分别使用 `-clock_fall`、`-rise`、`-fall` 和 `-add_delay`；不能套用单沿示例。

### 11. 输出时序约束

`set_output_delay` 描述下游器件相对于参考时钟对 FPGA 输出数据的建立/保持要求，并结合板级数据/时钟差异形成边界条件。

常见概念形式：

$$
OutputDelay_{max}=T_{setup,ext}+T_{dataPCB,max}-T_{clockPCB,min}+Margin
$$

对于要求时钟沿后继续保持数据的接口，Vivado/SDC 中 `-min` 常表现为负值：

$$
OutputDelay_{min}=-T_{hold,ext}+T_{dataPCB,min}-T_{clockPCB,max}-Margin
$$

```tcl
# 以下 2.5 ns / -0.8 ns 仅为示例
set_output_delay -clock io_virtual_clk -max 2.5 \
    [get_ports {data_out[*]}]
set_output_delay -clock io_virtual_clk -min -0.8 \
    [get_ports {data_out[*]}]
```

负号不是固定背诵规则；它来自所选参考沿、下游 `Thold` 定义和走线差。必须画清外部 launch/capture 时间轴后再代数计算。

### 12. CDC/RDC 约束

#### 12.1 CDC

- 单比特慢变化电平：通常采用两级或多级同步器。
- 单周期脉冲：采用脉冲展宽、toggle 或握手，不能假设两级同步器必然捕获。
- 多比特数据：采用握手、异步 FIFO 或保持数据稳定的协议；逐位同步可能产生字间不一致。
- Gray code：适合特定计数/指针场景，仍需结构与延迟关系检查。

切断异步时钟间路径后，仍须使用 `report_cdc` 审查结构。若使用 `set_max_delay -datapath_only` 管理某些 CDC 数据路径，需理解它忽略 skew 且会影响相应 hold 分析，不能当作通用模板。

#### 12.2 RDC 与异步复位

常用策略是“异步断言、同步释放”。异步复位释放涉及 recovery/removal；直接对整个复位网络做宽泛 `set_false_path` 可能掩盖释放风险。应确认：

- 每个时钟域是否有独立的复位同步释放链；
- 同步器属性和布局是否符合项目方法学；
- 复位域之间是否存在数据/控制依赖；
- `report_cdc`、方法学检查及实现后报告是否存在告警。

### 13. 时序例外及功能依据

#### 13.1 `set_false_path`

仅当路径在功能上永远不需要时序检查，或其时序安全性由另一种明确机制保证时使用。

```tcl
# 示例对象名；只有在功能证明成立时才可采用
set_false_path -from [get_cells src_reg] -to [get_cells dst_reg]
```

- **功能依据：**路径永不被功能模式激活，或跨域协议已独立保证安全。
- **分析后果：**指定路径不再进行相应 setup/hold 分析。
- **验证：**检查对象集合、`report_exceptions`、关键 timing path，并通过功能/CDC 验证证明路径确实无需 STA。

#### 13.2 `set_multicycle_path`

多周期路径必须来自“捕获使能不是每拍有效”等功能事实，而不是因为组合逻辑太长。

```tcl
# 示例：功能上明确允许 3 个周期完成
set_multicycle_path 3 -setup \
    -from [get_cells src_reg] -to [get_cells dst_reg]
set_multicycle_path 2 -hold \
    -from [get_cells src_reg] -to [get_cells dst_reg]
```

- **功能依据：**目的寄存器只在对应周期使能，数据在窗口内保持有效。
- **分析后果：**setup 捕获关系移动；同域常见配置需用 `N-1` 的 hold 调整恢复预期 hold 关系。
- **验证：**用 `report_timing` 检查实际 launch/capture edge；仿真或形式验证捕获使能；跨频率/相移场景必须单独推导 `-start/-end`。

如果寄存器每拍都可能采样，正确方向通常是流水线、重构逻辑或降低频率，而不是 multicycle。

#### 13.3 `set_max_delay` / `set_min_delay`

用于为特定路径声明明确的最大/最小路径延迟要求。

```tcl
# 示例值与对象，必须由接口/架构要求推导
set_max_delay 4.0 -from [get_cells src_reg] -to [get_cells dst_reg]
set_min_delay 0.5 -from [get_cells src_reg] -to [get_cells dst_reg]
```

- **功能依据：**协议或架构直接规定端到端最大/最小延迟。
- **分析后果：**覆盖默认路径 requirement；`-datapath_only` 还会改变 skew/hold 处理，需特别谨慎。
- **验证：**检查约束命中的路径数量、实际 path requirement 与是否意外覆盖正常寄存器路径。

### 14. 约束顺序、覆盖与对象选择

XDC 是顺序执行的 Tcl。推荐把依赖关系写清，而不是只记“最后一条总会生效”。当多个时序例外覆盖同一路径时，还存在例外优先级和对象范围差异；同优先级且等效覆盖时，后执行约束才可能覆盖前者。

推荐组织顺序：

1. Primary clocks
2. Virtual clocks
3. Generated clocks
4. Clock uncertainty / jitter
5. Input / output delays
6. Clock groups / clock false paths
7. False paths
8. Max delay / min delay
9. Multicycle paths
10. Case analysis / disable timing

对象选择原则：

- 使用 `get_ports`、`get_pins`、`get_cells` 前先确认返回对象非空且数量符合预期。
- 避免仅凭层级名称和宽泛通配符覆盖大量路径。
- 不把“ports > pins > cells”当作通用优先级口诀；以实际 exception 覆盖范围和报告为准。
- 多个 XDC 文件必须保证依赖顺序，尤其是时钟先于引用该时钟的约束读取。

### 15. 约束覆盖与未约束路径

约束完成不等于覆盖完整。至少检查：

- 所有时序端点是否有时钟；
- 所有常规输入/输出是否同时具有合适的 min/max delay；
- generated clock 是否漏建或重复创建；
- 是否有多时钟驱动的时钟引脚；
- 是否存在宽泛 false path 或 clock groups 掩盖有效路径；
- 是否有无约束内部端点、组合环路、锁存环路；
- 例外约束是否命中 0 条或远超预期数量的路径。

## 三、顺序：Vivado 工程落地流程

### 16. 推荐执行顺序

#### 第 1 步：梳理时钟树与接口

列出每个时钟的来源、频率、用途、经过的缓冲/IP、目标域和复位；同时列出所有外部同步接口及参考时钟位置。

#### 第 2 步：建立主时钟、虚拟时钟和衍生时钟

先写 `create_clock`，再确认自动/手工 generated clocks。运行：

```tcl
report_clocks
report_clock_networks
```

#### 第 3 步：声明时钟关系

根据时钟拓扑和系统功能判断同步、异步或互斥，不从名称猜测。运行：

```tcl
report_clock_interaction
```

#### 第 4 步：计算 I/O 时序预算

从外部器件数据手册、PCB 数据/时钟走线延迟及系统裕量推导每个接口的 `-min/-max`。保存计算依据，不在 XDC 中留下来源不明的魔法数字。

#### 第 5 步：审查 CDC/RDC

先确认同步器、握手、异步 FIFO、Gray code 和复位释放结构，再决定是否以及如何切断不适合常规 STA 的路径。

```tcl
report_cdc
```

#### 第 6 步：最后添加时序例外

每条例外记录：功能依据、对象范围、分析后果、验证方式。没有功能证明，就不添加例外。

#### 第 7 步：检查约束完整性

```tcl
check_timing
report_exceptions
report_methodology
report_timing_summary
```

#### 第 8 步：实现后签核

综合后的 net delay 可能只是估计；完整布线后的报告基于实际路由，才适合作为最终 timing signoff。除 setup/hold 外，还要复查 recovery/removal、pulse width、CDC 和方法学告警。

### 17. 时序违例闭环

```mermaid
flowchart LR
    A[发现时序违例] --> B[确认时钟与约束正确]
    B --> C[识别检查类型和真实路径]
    C --> D[分解逻辑/布线/skew/uncertainty/扇出]
    D --> E[选择架构、RTL或物理修复]
    E --> F[重新实现]
    F --> G[检查setup、hold、CDC与功能回归]
    G -->|仍失败| B
    G -->|通过| H[布线后签核]
```

分析单条路径时记录：

1. Check type：setup、hold、recovery、removal 或 pulse width。
2. Startpoint / Endpoint。
3. Launch clock / Capture clock 及有效边沿。
4. Requirement、Arrival、Required、Slack。
5. Logic delay、Route delay、Clock skew、Uncertainty、Fanout。
6. 生效的 exception 及其功能依据。

### 18. Setup/Hold 修复方法对照

| 问题 | 优先检查 | 常见有效修复 | 不可靠做法 |
| --- | --- | --- | --- |
| Setup 违例 | 约束、逻辑级数、routing、扇出、skew | 加流水级、重构逻辑、降低扇出、使用 DSP/BRAM、改善布局、合理降频 | 无功能依据地设 multicycle/false path |
| Hold 违例 | 时钟 skew、最短数据路径、约束 | 让实现工具插入/调整数据延迟、改善时钟与路由；必要时修正架构 | 单纯降低时钟频率 |
| Recovery/Removal | 复位释放结构、复位域 | 异步断言同步释放、每域同步器、降低复位扇出风险 | 宽泛 false path 掩盖整个复位网络 |
| CDC 告警 | 跨域协议、同步结构 | 同步器、握手、异步 FIFO、Gray code | 只加 `set_clock_groups` 后认为已安全 |

### 19. 常见错误与后果

| 错误 | 后果 |
| --- | --- |
| 写成 `creat_clock` | 命令不存在，时钟未创建 |
| 只写 I/O `-max` 不写 `-min` | hold/min 分析缺少真实外部边界 |
| 固定套用 setup/hold 数值 | 忽略器件、PVT、原语和分析角差异 |
| 用 multicycle 修复普通长组合路径 | 报告可能变绿，但电路仍每拍采样错误数据 |
| 把所有 CDC 都设 false path | 掩盖错误的同步结构和多比特一致性问题 |
| 异步复位全部 false path | 可能掩盖 recovery/removal 与释放风险 |
| 认为 XDC 总是“最后一条生效” | 忽略例外优先级、对象范围和多约束共存 |
| 只看 WNS | 无法判断 hold、CDC、未约束路径和真实根因 |
| 用综合后报告做最终签核 | 互连延迟仍可能是估计值 |

## FAQ

### 时序报告全绿，硬件就一定安全吗？

不一定。遗漏时钟、缺失 I/O delay、过宽 false path 或错误 clock groups 都可能让工具少分析路径。必须先确认约束完整性和 CDC/RDC 安全性。

### 为什么 `set_output_delay -min` 经常是负数？

因为下游器件要求时钟沿后保持数据，相对于该捕获沿，FPGA 输出“最早允许变化”的边界常落在负的 SDC delay 表达中。最终数值仍需结合参考沿和 PCB 时钟/数据差计算。

### 组合逻辑太长能否直接设 multicycle？

不能。只有功能上确实允许多个周期且捕获使能关系可证明时才可使用；否则应流水化或重构逻辑。

### 异步时钟之间是否必须 `set_clock_groups -asynchronous`？

需要先检查所有跨域路径和 CDC 结构，再选择适合的约束。全局 clock groups 会切断两个时钟组之间的分析，可能覆盖你原本希望用 `set_max_delay -datapath_only` 管理的路径。
